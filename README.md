# KiranaLedger: Agentic Bill Extraction & Ledger Assistant

**Live:** https://main.d2djabvtfe8b0r.amplifyapp.com

## The Problem

Small shop owners handle supplier bills manually. They photograph or keep paper copies, then tally totals into a notebook or spreadsheet by hand at the end of the day. There is no easy way to catch a duplicate bill, a price that has jumped from last time, or a payment that is coming due, until it is already a problem.

## What We Built

A shop owner photographs a supplier bill. The system reads the line items, checks them against the existing ledger, and **holds the bill for review if something looks wrong** rather than filing it silently.

Flow: photo upload → extraction → checks against history → ledger entry, with flags attached

The checks are the point. Reading a bill is a solved problem; deciding whether this bill should be trusted is not:

- **Duplicate detection.** A matching bill number from the same supplier stops the write. A near identical total inside a short window is flagged as suspicious, which matters because the second photograph of a bill rarely totals to exactly the same number, and an equality check would miss it.
- **Price jump detection.** A unit price is compared against the last recorded price for that item from that supplier. It has to clear both a percentage and a rupee floor, so a ₹4 item going to ₹5 does not generate noise.
- **Due dates.** Surfaced on the bill and on the ledger, sorted soonest first.

## Where AWS Fits

| Stage | AWS Service | What it does |
|---|---|---|
| Bill photo upload | **Amazon S3** | Presigned PUT, so the photo goes phone to bucket without passing through a function |
| Line item extraction | **Amazon Textract** (`AnalyzeExpense`) | Returns labelled vendor, bill number, dates, totals and grouped line items |
| Ledger storage | **Amazon DynamoDB** | Single table, bills and per item price history, written in one transaction |
| Hosting | **AWS Amplify Hosting** | Next.js SSR on Web Compute, deploying from `main` |
| Runtime permissions | **IAM** | A scoped compute role, no credentials in the app |

### Why Textract rather than a vision model

`AnalyzeExpense` is purpose built for invoices and receipts, so it returns labelled fields and grouped line items directly instead of requiring prompt engineering and schema enforcement. It also gives per field confidence scores. Bedrock model access was not available on our account during the hackathon, which forced the decision early, but the result is a better fit for this specific problem than a general vision model would have been.

Flag wording is generated by a free model through OpenRouter. It writes prose from facts the code has already computed and never does arithmetic, so severity and every number stay under our control.

### What Textract gets wrong, and what we do about it

On a deliberately degraded photo, Textract returned a unit price of ₹8 instead of ₹88, **at 99.5% confidence and with no warning**. Its confidence score describes how sure it is of the characters it saw, not whether the numbers make sense.

What catches it is the row contradicting itself: 20 units at ₹8 is not ₹1,760. The line total is trusted there, because the bill total corroborates it and the rate corroborates nothing, so the rate is recovered by division and a warning is raised. Item names on that photo are still misread, and that is the honest limitation. The money lands correctly, which is what every downstream comparison depends on.

## Getting Started

```bash
git clone https://github.com/PranavV205/kiranaledger.git
cd kiranaledger
npm install
cp .env.example .env.local   # then fill in the values
npm run dev
```

You need an S3 bucket, a DynamoDB table with a `gsi1` index, and AWS credentials with S3, Textract and DynamoDB access. Check your setup before building anything:

```bash
curl localhost:3000/api/health?deep=1
```

That exercises the real IAM action behind each service and names whichever one is misconfigured.
